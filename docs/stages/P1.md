# P1 · Eager 单流生成（正确性里程碑）— 阶段笔记

> 状态：**全部验收达成（2026-09-21）**——fp32 位级一致 + bf16 实现差异远小于 bf16 固有损失 + greedy 128 token 一致 + bench 6× 对比
> 日期：2026-09-21

## 阶段定位

P1 是整个路线的**正确性基石**。P0 已建好 golden 工具链（HF 逐层 dump + 对拍），P1 要做的是：**在不引入任何性能优化的前提下，把模型前向 + 自回归生成写对**。性能优化（KV cache、批调度、CUDA Graph）全部推迟到 P2+，因为在一个错误的基线上优化只会放大错误、让排查无从下手。

**设计决策**：

1. **Eager 重算作为最差基线**：每生成一个 token 都把**完整序列**重新跑一遍前向（`forward_last_logits(ids)` 传全序列，无 cache）。这是性能最差的实现——生成 N 个 token 的总 FLOPS 是 O(N²·L) 而非 O(N·L)——但它**最简单、最不容易出错**：没有 cache 的索引管理、没有 prefill/decode 分离、没有形状变化。P1 的 TPOT 441ms（0.5B CPU）vs HF cache 版 74ms 的 6× 差距，正是 P2 要消灭的开销，这个数字是 P2 的动机证据。
2. **数值路径逐行对齐 HF `modeling_qwen2.py`（5.x）而非 vLLM**：vLLM 的模型代码经过 PagedAttention/CUDA Graph/quantization 等多层封装，不适合作为正确性参照。HF 的 eager 路径是**最直白的参考实现**，逐行对照能定位到任意一层的任意一个算子。P3+ 再向 vLLM 的工程结构靠拢。
3. **0.5B + 1.5B 双模型验证**：0.5B 用于快速迭代（CPU fp32 几秒跑完一轮对拍），1.5B 是目标模型用于最终验收。两个模型的 config 不同（0.5B head_dim=64 / 1.5B head_dim=128，层数 24 vs 28），能覆盖不同的架构参数组合。

## 本阶段结论

- P1 目标：config 驱动的 Qwen2 模型 + safetensors 加载 + 采样器 + 无 KV cache 的自回归循环（每步全量重算），数值路径逐行对齐 HF `modeling_qwen2.py`。
- **正确性三层证据**：
  1. **0.5B 同设备同 dtype（CPU fp32）对拍：29 个张量 diff = 0（位级一致）+ greedy 32 token 逐 token 一致** —— 逻辑（结构/权重加载/RoPE/GQA/tie_emb/采样路径）完全正确。29 = 1 embed + 24 层 × 1 hidden + 1 final norm + 1 logits + 1 greedy_ids。位级一致意味着不只是"差不多对"，而是每个比特都相同，排除了所有逻辑错误。
  2. **1.5B 跨设备（GPU fp32 golden vs CPU fp32 nano）对拍：29 个张量 max diff ≤ 3.4e-3（mean ~1e-5），全部 < 1e-2 容差** —— fp32 GEMM 归约顺序差异的正常量级。跨设备（GPU vs CPU）的 fp32 matmul 因归约顺序/分块策略不同，结果在 1e-3 量级有差异，这是 PyTorch 的已知行为，不是 bug。1e-2 容差远大于此差异、远小于逻辑错误（逻辑错误通常 >1）。
  3. **bf16 路径正确性验证（0.5B CPU 四组对比）**：HF 自身 fp32→bf16 固有损失 **22.58**，nano bf16 vs HF bf16 实现差异仅 **2.00**（远小于固有损失），nano fp32 vs HF fp32 = **0.0000**。1.5B GPU bf16 hidden_27 diff=3.0 + greedy 128 token 逐 token 一致 → **bf16 diff 是舍入正常累积，非 bug**。详见踩坑 8。
- **KV cache 价值量化（P2 的动机证据）**：同条件 0.5B CPU fp32，nano 重算版 TPOT **441ms** vs HF cache 版 **74ms**（**6×**）。重算版每步把全部序列重跑一遍，这就是 P2 要消灭的开销。

## 设计思路

### 为什么先正确性后性能

推理引擎的优化（KV cache、PagedAttention、CUDA Graph、连续批处理）每一层都会引入新的数值路径。如果基模型就是错的，优化后的输出与"正确输出"的 diff 会混合"基模型 bug"和"优化引入的 bug"，无法分离。**先在 eager 重算下拿到与 HF 位级一致的基线，后续每个优化阶段都回归这个基线对拍**，任何 diff 退化都能立刻定位到该阶段引入的改动。

### 为什么逐层对齐而非端到端

端到端对拍（只比 greedy 输出 token 序列）能通过但隐藏中间层错误——例如某层的 RoPE 实现错了但恰好不影响 argmax。逐层对拍（比每一层的 hidden_states + logits）能定位到**哪一层的哪一个算子**出了问题。P0 的 `dump_hf.py` / `dump_nano.py` 各 dump 29 个张量，`check_diff.py` 逐个对比，就是为这个排查粒度服务的。

### 采样器处理顺序的数学原理

`sample/sampler.py` 的顺序是 **temperature 缩放 → top-k → top-p → softmax → multinomial**，对齐 vLLM v1 sampler。关键设计：

- **top-k 和 top-p 都在 logits 空间操作（置 -inf）而非概率空间**：置 -inf 后 softmax 时 `e^{-inf}=0`，被筛掉的元素概率精确为 0，剩余元素归一化后概率和 = 1。这比"在概率空间截断后重新归一化"更简洁，且避免了二次归一化的精度损失。
- **top-k 先于 top-p**（先粗筛再细筛）：top-k 把 vocab 从 ~150k 砍到 k 个，top-p 再在这 k 个里砍尾部累积超过 top_p 的部分。两个筛选都通过置 -inf 叠加在 logits 上，最后一次性 softmax + multinomial。
- **top-p 的 softmax 只是辅助**：top-p 内部的 `softmax(sorted_logits)` 只是为了算累积概率确定阈值，筛选动作仍是置 -inf，不是"对 top-k 结果做 softmax 然后取 top_p"。
- **temperature<=0 视为 greedy**：直接 argmax，跳过所有随机路径，保证 greedy 主路径零随机性（对拍时 seed 不影响 greedy 输出）。

**`config.py` — 实现要点与设计理由**：
- frozen dataclass（不可变，防止运行时误改 config）；`from_json` 直接读 HF config.json 顶层字段（不经 transformers config 类，避免对 HF 运行时的依赖，也让 config 加载在 P3+ 的 CUDA Graph capture 期间不会触发 HF 的懒加载逻辑）。
- `head_dim = raw.get("head_dim") or hidden//heads`：1.5B config **无 head_dim 字段**（0.5B 有），推导值 128 恰为隐式值。这个 fallback 对齐 HF `compute_default_rope_parameters` 的 `dim = getattr(config, "head_dim", None) or config.hidden_size // config.num_attention_heads`。
- `num_kv_groups`（GQA 分组数 = num_heads // num_kv_heads）/`eos_ids`（int|list 归一为 set）为派生属性（@property），不存原始值。
- 校验：`num_attention_heads % num_key_value_heads != 0` 直接 raise（GQA 要求整除）；`hidden_act != "silu"` 直接 raise（P1 范围声明，P3+ 扩展其他激活）。

**`models/qwen2.py` — 实现要点与设计理由**（数值路径逐行照抄 HF 5.x，不凭记忆）：
1. **RMSNorm**：fp32 中 `x * rsqrt(mean(x²)+eps)`，cast 回原 dtype 后再乘 weight。顺序：先在 fp32 下算归一化系数（避免 bf16 下 mean 的精度损失），再 cast 回 x.dtype 乘 weight（weight 是 bf16）。这个顺序与 HF 完全一致，调换会导致 1e-3 量级差异。
2. **RotaryEmbedding**：`inv_freq = 1/(theta^(arange(0,d,2)/d))` fp32 buffer（`persistent=False` 不存 checkpoint）；forward 中 `inv_freq ⊗ position_ids` 外积 → `cat(freqs, freqs)`（**前后拼接而非交错**，对应 `rotate_half` 的 `cat(-x2, x1)` 切法）→ cos/sin 在 `torch.autocast(enabled=False)` 强制 fp32 计算（RoPE 对精度敏感，bf16 下 cos/sin 误差会被 q/k 放大），返回时 `.to(x.dtype)`。cos/sin **只依赖 inv_freq + position_ids，不依赖 x**——这个性质是踩坑 8 排查的关键。
3. **apply_rotary_pos_emb**：cos/sin 沿 head 维 `unsqueeze(1)`，`q*cos + rotate_half(q)*sin`，rotate_half 为 `cat(-x2, x1)`（前半取负拼后半，对应 cat(freqs,freqs) 的双倍频率构造）。
4. **Attention**：QKV **bias=True**（Qwen2 特有，区别于 LLaMA 的 bias=False）、o_proj 无 bias；`view(b,s,heads,hd).transpose(1,2)` 把 head 维提到 dim=1；KV 经 `repeat_kv`（expand+reshape 等效 repeat_interleave，**不实际复制内存**，expand 是视图操作）展开 6 倍（num_kv_groups=6）；`F.scaled_dot_product_attention(scale=head_dim**-0.5, is_causal=True)`——与 golden dump 时 HF sdpa 同路径（P1 不用 flash_attn，SDPA 在 bf16 下走 memory-efficient kernel 足够）。
5. **结构**：DecoderLayer 双 pre-norm residual（`h = h + attn(norm1(h))`，`h = h + mlp(norm2(h))`）；Qwen2Model 级共享单个 rotary_emb（所有层用同一份 cos/sin，因为 position_ids 一致）；`output_hidden_states=True` 时返回 `[embed, L1..LN]` 且 **末元素替换为 final norm 之后**（对齐 HF 5.x 语义，见踩坑 2）。
6. **load_weights**：自研命名与 HF 完全同名（`model.*`/`lm_head.weight`），映射近乎恒等；tie 时 `weights["lm_head.weight"] = weights["model.embed_tokens.weight"]`（见踩坑 1）；`load_state_dict(strict=False)` 后 missing/unexpected 双校验。加载前模型已 `.to(dtype)`，copy_ 无 dtype 转换损失（见踩坑 6）。

**`sample/sampler.py` — 实现要点与设计理由**：
- temperature<=0 直接 argmax（greedy 零随机，跳过所有随机路径，对拍时 seed 不影响 greedy 输出）。
- top-k 用 `topk(...)[0][-1]` 阈值法置 -inf（取第 k 大的值作阈值，低于阈值的置 -inf；用严格小于 `<` 保留并列值）。
- top-p 用 sort→softmax→cumsum，`mask=(cum-probs)>top_p` 保留首个越界 token（`(cum-probs)` 偏移一位确保首个 token 永远保留），scatter 回原索引置 -inf。
- `torch.multinomial(generator=独立 Generator)`，generator 按设备类型创建（CPU generator 不能用于 CUDA tensor，会报错）。
- 处理顺序对齐 vLLM v1 sampler：**temperature → top-k → top-p → softmax → multinomial**，top-k/top-p 都在 logits 空间置 -inf，最后统一 softmax。

**`runner.py` — 实现要点与设计理由**：
- `NanoRunner` 持有 config/model/sampler；`forward_last_logits(ids)` 每步传**全序列**（无 cache，这就是最差基线的设计——O(N²) FLOPS，P2 的优化目标）。
- `generate()` 循环 argmax/采样，eos 集合来自 config（int|list 归一为 set）。
- 模型加载顺序：`Qwen2ForCausalLM(config).to(device, dtype).eval()` → `load_weights(path)`。先 `.to(dtype)` 再 load，确保 copy_ 是 bf16→bf16 无损（见踩坑 6）。

**`dump_nano.py` — 实现要点与设计理由**：
- 输入 ids 从 `--ref` golden 的 meta.json 读取（**绝对保证与 HF golden 输入一致**，不依赖 tokenizer 重新编码可能产生的差异）。
- dump 格式与 dump_hf 完全对称（29 个 npy：embed + 24 hidden + final norm + logits + greedy_ids）。
- greedy 循环含 eos（对齐 HF generate 语义），eos 集合并入 generation_config（见踩坑 5）。
- `--gen-tokens` 可覆盖 ref 的生成长度（CPU 慢机可调小，用于快速冒烟）。

**`verify_bf16_noise.py` — 实现要点与设计理由**：
- 四组对比定性 bf16 diff 来源：A) HF fp32 vs HF bf16（bf16 固有精度损失）、B) nano fp32 vs nano bf16（自研侧固有损失）、C) nano bf16 vs HF bf16（实现差异）、D) nano fp32 vs HF fp32（逻辑差异）。
- 判据：C 若与 A 同量级 → bf16 正常累积；C >> A → 实现有 bug。D 应 ~0（逻辑等价）。
- 用 0.5B CPU 跑（快，几秒），结论可外推到 1.5B GPU bf16（bf16 舍入行为是 dtype 固有，与设备/模型大小无关）。

## 踩坑记录（本阶段干货最多的一节）

1. **`state_dict()` 对共享参数不去重**：`lm_head.weight = embed_tokens.weight`（tie）后，`named_parameters()` 去重只报一处，但 `state_dict()` 遍历模块树会包含两个键。于是 `load_state_dict(pop 掉 lm_head)` 报 `missing: ['lm_head.weight']`——明明共享却还要"存在"。**发现过程**：load 后 strict 校验报 missing，初看以为 tie 没设对，但 `named_parameters` 确实只有 embed。**排查**：打印 `state_dict().keys()` 发现有 `lm_head.weight`，才意识到 state_dict 不去重。**修复**：tie 时把 embed 权重复制一份给 lm_head 键（copy_ 到同一 Parameter 两次，幂等）。

2. **HF 5.x 的 `output_hidden_states` 末元素是 final norm 之后的输出**（4.x 时代 norm 前后被区别对待的行为差异）。**发现过程**：0.5B 对拍 24 层全 diff=0、logits diff=0、唯独 hidden_24 差 193——量级悬殊不像舍入。**排查**：把自研的 `norm(最后一层输出)` 与 HF 末元素比，diff=0 即证实 HF 末元素是 norm 后。**修复**：`all_hidden[-1] = norm(hidden_states)`。**教训**：HF 的 hidden_states 语义跨版本有变化，不能凭记忆，必须实测。

3. **HF `generate()` 默认走 KV cache 增量路径**，与全量重算的 kernel/归约顺序在 fp32 下也有 ~1e-6 差异；top-2 接近时 argmax 翻转，自回归输出从分叉点开始彻底不同。**发现过程**：0.5B greedy 对拍前几步一致、某步突然分叉，且分叉点不稳定（改 prompt 位置变）。**排查**：对比单步 logits 发现 diff ~1e-6，但 top-2 logit 差距也 ~1e-6，argmax 翻转。**修复**：对拍判据必须是**同路径**——dump_hf 加 `use_cache=False`（0.5B 修复后 32 token 位级一致）。**教训**：fp32 下 1e-6 的差异在 argmax 边界上也会翻转，对拍必须同计算路径。

4. **`generation_config.json` 的 `repetition_penalty=1.1` 在 `do_sample=False` 时仍生效**——HF 的"greedy"不是纯 argmax！**发现过程**：0.5B greedy 对拍在第 6 步（首次 token 重复处）分叉，且分叉点稳定。**排查**：读 HF `generate()` 源码发现 `repetition_penalty` 在 `do_sample=False` 时仍对 logits 做惩罚，Qwen 官方 generation_config 带此字段。**修复**：golden 定义为纯 greedy（`repetition_penalty=1.0`），并在 P1 笔记中记录该语义约定。**教训**：HF 的 "greedy" 语义不等于纯 argmax，必须显式关闭所有 logits 惩罚。

5. **eos 是列表不是单值**：generation_config `eos_token_id=[151645, 151643]`，自研只用 config.json 的单值会在停止条件上与 HF 不一致。**发现过程**：greedy 输出长度与 HF 不一致（nano 多生成几个 token）。**排查**：对比 generation_config 与 config.json 的 eos 字段，发现前者是列表。**修复**：归一为 set 合并处理。

6. **torch bf16 权重加载顺序**：模型先 `.to(dtype)` 再 `load_state_dict`（copy_ bf16→bf16 无损）；若先加载后转型，fp32 存储的"bf16 值"权重会走不同 GEMM 路径，对拍必挂。**发现过程**：0.5B 对拍 diff 不为零但很小（~1e-4），疑似精度问题。**排查**：对比加载顺序，发现先 load 后 to 会多一次 fp32→bf16 的 cast。**修复**：调整顺序为 `.to(dtype)` → `load_weights`。

7. WSL2 GPU 透传今日再次间歇性失效（`wsl --shutdown` 可解）——工程上依赖 GPU 的验证步骤都设计了 CPU 降级路径（0.5B fp32 自检、1.5B fp32 跨设备对拍）。

8. **bf16 hidden diff=3.0 的定性判断**（本阶段最曲折的排查）：1.5B GPU bf16 对拍 hidden_27 max diff=3.0，初看像 bug。**排查过程**：
   - **第一步**：逐层二分定位——ln1=0、q_proj=0、attn=0.27 → 锁定 self_attn 内部。
   - **第二步**：读 HF `sdpa_attention.py`，发现 `enable_gqa` vs `repeat_kv` 两条路径，patch 修复后 diff 不变 → **假设错误**，两者数值等价。
   - **第三步**：函数级对比脚本显示 cos/sin diff=0.578 → 以为找到 RoPE bug。
   - **第四步**：读 HF `maybe_autocast`、`dynamic_rope_update`、`nn.Buffer`，逐一排除——default rope 下装饰器是 no-op，`nn.Buffer` 与 `register_buffer` 在 `.to(bf16)` 下行为相同。
   - **第五步**：意识到 **cos/sin 只依赖 inv_freq + position_ids（不依赖 x）**，CPU fp32 位级一致已证明逻辑等价，0.578 不可能来自实现差异。
   - **第六步**：写 `verify_bf16_noise.py` 四组对比定性：bf16 相对 fp32 的**固有精度损失就有 22.58**，nano vs HF 在 bf16 下的 2-3 diff 完全是舍入正常累积。
   - **教训**：bf16 下逐层 diff 的绝对值无意义，必须与 bf16 固有损失对比才有意义；**greedy 逐 token 一致才是功能正确性的硬判据**。排查走了弯路是因为一开始没建立"bf16 diff 的正常量级是多少"的参照系。
