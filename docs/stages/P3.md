## 本阶段结论

- P3 目标：把 P2 的连续预分配 KV cache（浪费 15%）换成按 block 分页，消除内部碎片；
  decode attention 从 SDPA（假设 KV 连续）换成自研 Triton paged kernel（block_table 间接寻址）。
- **正确性（CPU fp32）**：
  1. **三路对拍**：torch 朴素 paged attention vs 连续 SDPA vs 自研 Triton kernel，
     seq_len ∈ {1,5,16,17,33,65,100}、block_size ∈ {4,8,16,32,64}，max diff < 5e-7
  2. **分页 generate vs 连续 cache generate 逐 token 完全一致**（0.5B CPU fp32，
     block_size 8/16/32/64 + 跨 block 边界 prompt）
  3. **测试套件 11 项**（`tests/test_p3_correctness.py`），全测试 **22 passed, 1 skipped**
- **KV 浪费率**：分页后仅浪费最后一个 block 的尾部
  - 1025 token → **1.44%**（< 2% 验收达标）
  - 1024 / 8192 / 32768 token → **0%**（整除 block_size）
  - 对比 P2 连续预分配 **15%**
- **Triton kernel 验证手段**：无 GPU 时用 `TRITON_INTERPRET=1` 在 CPU 上解释执行 kernel 做逻辑对拍

**`core/block_pool.py` — 实现要点**
- `KVCacheBlock`：`block_id`（物理存储第一维下标）+ `ref_cnt`（P3 只用 0/1，P6 COW 复用）。
- `BlockPool`：`deque` 做 FIFO free list。相比 vLLM 的双向链表（为 O(1) 中段删除/prefix 淘汰），
  P3 无淘汰需求，FIFO 足够且**分配顺序确定**（同 seed 同输入必然得到相同 block_id 序列，便于对拍复现）。
- 守卫：`allocate` 耗尽 raise；`allocate_n` 先校验再分配（不产生半分配）；`free` 检查 ref_cnt 防重复释放。

**`core/paged_kv_cache.py` — 实现要点**
- 布局 `[num_layers, num_blocks, block_size, num_kv_heads, head_dim]`，K/V 各一份。
- `slot_mapping(block_table, start_pos, num_tokens)`：token t 的物理 slot = `block_table[t // block_size] * block_size + (t % block_size)`。
- `reshape_and_cache`：把 `[num_blocks, block_size, ...]` view 成 `[num_blocks*block_size, ...]`，
  用 slot_mapping 做一次高级索引 scatter——slot 是物理地址，天然支持乱序/跨 block。
- `waste_rate = 1 - written_tokens / allocated_slots`（只浪费最后一块尾部）。

**`attention/triton_paged_attn.py` — 实现要点**
- grid = `(num_heads,)`，每 program 处理 1 个 head 的 1 个 query token（decode）。
- **online softmax**：逐 block 遍历，维护 running max `m_i` / sum `l_i` / 累加器 `acc`，
  用 `alpha = exp(m_i - m_new)` 修正历史累加——不物化完整 `[seq_len, head_dim]` KV（分页省显存的关键）。
- **block_table 间接寻址**：`physical = tl.load(block_table_ptr + blk_i)` 后按物理块偏移 gather K/V。
- GQA：`kv_head_idx = head_idx // num_queries_per_kv`，Q 头共享同一组 KV。
- 边界：`n_mask = (blk_i * block_size + offs_n) < seq_len` 处理最后一块的尾部空洞。

**`attention/metadata.py` + `backend.py` — 实现要点**
- `AttentionMetadata` 收拢 `is_prefill` / `slot_mapping` / `block_table` / `seq_len` / `attn_impl`（解 P0-06）。
- `PAGED_ATTN_BACKENDS = {"torch": ..., "triton": ...}` + `get_paged_attn(impl)`（解 P0-07）。

## 踩坑记录

1. **`_written_tokens` 按层累加导致 waste_rate 为负**：`PagedKVCache.write` 每层调用一次，
   初版每层都 `+= num_tokens`，28 层累加 28 倍 → `1 - 28*seq/allocated` 变负数。
   修复：`if layer_idx == 0` 才累加，按逻辑 token 统计一次。教训：**跨层共享的统计量只能在一个"代表层"累加**。

2. **bench 脚本重复 prefill 导致重复分配 block**：初版 `timed(lambda: r._prefill_paged(ids))` 后又调一次取 logits，
   两次 prefill 各分配一套 block。修复：`ttft, logits = timed(...)` 一次拿全。教训：**带副作用的函数不能为了取返回值再调一次**。

3. **无 GPU 环境验证 Triton kernel**：agent shell `torch.cuda.is_available()=False`。
   解法：`TRITON_INTERPRET=1` 让 kernel 在 CPU 上解释执行（numpy 语义），对拍 torch 朴素实现。
   入口加 `_INTERPRET` 判断，避免误报"需要 CUDA"。**这是无 GPU 时验证 kernel 逻辑的正确姿势**。

4. **block_size 与序列长度共同决定浪费率**：短序列（68 token）下 block_size=32 浪费 29%，
   但长序列（1025 token）下 block_size=16 浪费仅 1.44%。**分页的浪费率必须标注序列长度**，
   否则"waste < 2%"的验收会在短序列上被误判失败。

5. **Triton kernel 缺 `offs_n < block_size` 掩码**（审查发现）：`BLOCK_N = next_power_of_2(block_size)`，
   非 2 幂 block_size 时 `BLOCK_N > block_size`，`offs_n` 会越过当前物理块边界读到相邻块内存。
   `n_mask` 只检查 `< seq_len` 不检查 `< block_size`。当前 block_size 均为 2 幂不触发，
   但属潜在 bug。修复：`n_mask = n_mask & (offs_n < block_size)`。

6. **`_written_tokens` 跨 generate 累加不重置**（审查发现）：`_free_paged` 释放块但不重置
   `_written_tokens`，同一 runner 第二次 generate 的 `waste_rate` 会变负。仅影响报告不影响正确性。
   修复：`_prefill_paged` 开头重置 `_written_tokens = 0`。
