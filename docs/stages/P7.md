## 本阶段结论

- **目标**：把 decode 前向从「每步几百次 kernel launch 的 eager 执行」变成「一次图回放」。
- **实现**：`FULL_DECODE_ONLY` 的简化版（vLLM `CUDAGraphMode.FULL_DECODE_ONLY = (FULL, NONE)`）——
  decode 批全图回放，其余批（prefill / 超桶）回退 eager；**不做 PIECEWISE**（需编译栈，roadmap §2 已裁剪）。
- **正确性**：新增 `tests/test_p7_correctness.py`（10 项）；全量 `tests/` **115 passed**。
- **验收（roadmap §P7 的 4 条）**：

| 判据 | 目标 | 实测（1.5B/bf16） | 证据 |
| --- | --- | --- | --- |
| 输出与 eager 逐 token 一致（含边界 batch） | 一致 | ✅ n=1/3(padding)/4(满桶)/5(超桶回退)/长上下文全覆盖 | `test_p7_correctness.py` |
| uniform decode 全部命中图 | 100% | ✅ hit_rate=1.00（bs 1→32 全部；混合负载亦 1.00） | `p7_bench.json` |
| kernel launch 开销占比 | 10–30% → ~1% | ✅ **26.1% → 0.76%** | `p7_profiler.json` |
| TPOT 相对 P4 下降 | 15–25% | ✅ **超额**：bs=8 49.5→9.5ms（5.21×），bs=32 102.9→10.2ms（10.14×） | `p7_bench.json` |

- **一句话结论**：P7 的真实收益比 roadmap 预设的 15–25% 大一个量级，原因是 **P4 的 eager decode
  基线本身含大量 host 侧开销**（逐层构建 2D 块表张量 + 每层 kernel launch），图捕获把这两块一起消掉了；
  归因实验（同一静态 buffer，只切图）显示纯图收益稳定在 **~2.6–2.8×**，静态 buffer 额外贡献 **1.5–3.8×**（随 batch 增长）。

## 架构设计

### B1 · 分派：两级，不做 dispatcher 全套

| 条件 | 模式 | 说明 |
| --- | --- | --- |
| decode 批且 `n ≤ max_bucket` | **图回放**（FULL） | uniform decode：每请求恰 1 token，形状由桶决定 |
| 其余（超桶 / 未启用 / 非 CUDA / 非 triton） | **eager**（NONE） | 逐请求 list 寻址或批量 triton kernel |
| prefill 批 | **eager** | P7 只捕获 decode，prefill 仍走 varlen（roadmap 原案） |

对照 vLLM：`CudagraphDispatcher.dispatch()` 建 FULL 键时用
`num_reqs = num_tokens_padded // uniform_decode_query_len`（本快照 `cudagraph_dispatcher.py:141-146`），
即 **FULL 图只服务 uniform decode**；非 uniform 只能 PIECEWISE。nano 的 decode 前向天然 uniform
（prefill 是另一次前向），因此不需要 BatchDescriptor 五元键与多 routine。

### B2 · 桶与 padding（`nano_vllm/cudagraph/`）

| 组件 | 职责 |
| --- | --- |
| `DecodeBuffers` | 一个桶的全套静态输入：`input_ids/positions/slot_mapping`（`[bucket]` int64）、`block_table`（`[bucket, max_blocks]` int32）、`seq_lens`（`[bucket]` int32）、`logits`（`[bucket, vocab]`，捕获时在池内创建） |
| `DecodeGraphRunner` | 分桶捕获（含 warmup）/ 回放 / 命中埋点 / 回退计数 |

- 桶 `1/2/4/8/16/32`（roadmap §1 的 16GB 建议档位）；n 向上取最近的桶，多出来的行是 padding。
- **padding 行必须安全**：`reshape_and_cache` 不看 seq_len，padding 行会**真实写入** K/V。
  故 `BlockPool.reserve()` 永久预留 1 个 scratch 块（不进 free 队列、跨 `reset()` 保持），
  padding 行的 `slot_mapping` 全部指向该块、`seq_lens=1`、块表首列指向它 —— 读写都不碰真实请求。
  代价：可用块 -1（1.5B 下 num_blocks≈1.3 万，可忽略）。
- **布局**：图内前向按 `b = 桶`、`s = 1` 组织（每行一个请求的 1 个 token）—— 与 vLLM 的
  persistent buffer 布局一致；`logits[:, 0]` 即 `[bucket, vocab]`。
- **warmup**：每桶先按 padding 配置跑 `warmup_runs=2` 次 eager（触发 Triton 编译/autotune 与分配器预热），
  再 `torch.cuda.graph(g, pool=...)` 捕获；**第一个桶建池，其余共享同一图池**（省显存，顺序回放无别名风险）。
- **输出按整桶计算**：静态形状下无法按动态 `logits_indices` 只算有效行，padding 行的 lm_head 白算
  （代价 ≈ `(bucket-n) × vocab × hidden`）。这是与 vLLM 的一个已知差异，量化见下方 padding 小节。

## 实测数据（均在 Qwen2.5-1.5B-Instruct / bf16 / RTX 4070 Ti SUPER 上测得，不外推）

口径：prompt=128 token、max_new=32、budget=2048、num_blocks=4096（固定池）、attn=triton、
每配置预热 1 次 + 重复 5 次取中位数；TPOT = **decode-only step** 墙钟时间。

### 1. TPOT 曲线与收益归因（`bench/results/p7_bench.json`）

| batch | P4 eager (ms) | 静态 buffer + eager (ms) | P7 图 (ms) | 总加速 | 归因：静态 buffer × 图 |
| --- | --- | --- | --- | --- | --- |
| 1 | 36.14 | 24.47 | **8.80** | 4.11× | 1.48× × 2.78× |
| 2 | 41.88 | 24.95 | **9.55** | 4.39× | 1.68× × 2.61× |
| 4 | 39.69 | 25.30 | **9.84** | 4.03× | 1.57× × 2.57× |
| 8 | 49.51 | 25.83 | **9.51** | 5.21× | 1.92× × 2.72× |
| 16 | 68.47 | 25.93 | **9.57** | 7.15× | 2.64× × 2.71× |
| 32 | 102.88 | 27.43 | **10.15** | 10.14× | 3.75× × 2.70× |

**读法**：图回放后 TPOT 几乎与 batch 无关（8.8→10.2ms，memory-bound 平台期），
eager 则随 batch 线性恶化（逐层建块表张量是 O(batch) 的 host 工作）。
图本身贡献稳定 ~2.7×；**batch 越大，静态 buffer 的贡献越大**（1.48× → 3.75×）。

### 2. kernel launch 占比（`bench/results/p7_profiler.json`，batch=8）

| 指标（每 decode step） | P4 eager | P7 图 | 变化 |
| --- | --- | --- | --- |
| **kernel launch API 时间** | **11.82 ms** | **0.084 ms** | **141×↓** |
| graph launch（cudaGraphLaunch） | — | 1.23 ms | 每步一次回放 |
| H2D 拷贝（buffer 填充 + 采样 D2H） | 7.89 ms | 7.16 ms | 基本不变 → **新瓶颈** |
| GPU kernel 时间 | 29.89 ms | 8.08 ms | 2.9×↓（launch 空转消失） |
| **launch 占 TPOT** | **26.1%**（roadmap 预期 10–30%） | **0.76%（≈1%）** | ✅ 达标 |
| TPOT（未开 profiler） | 45.28 ms | 10.96 ms | 4.13× |

**新结论（P7 之后的方向）**：图化之后 **CPU 侧总 API 时间 8.68ms ≈ TPOT 10.96ms 的 79%**，
其中 H2D 拷贝占 7.2ms —— 静态 buffer 的填充成了下一道天花板。
可做的（归 P8/P9）：pin memory + `non_blocking` 拷贝、合并每步 5 次 `.copy_()` 为一次打包拷贝、
块表按行差异更新（只写变化列）。

### 3. 桶数 tradeoff（batch=32 为「只有 6 档能覆盖」的对照）

| 桶档 | 峰值显存 | 捕获耗时 | bs=16 TPOT | bs=32 TPOT / 命中率 |
| --- | --- | --- | --- | --- |
| `(1, 4, 16)` | 5.15 GB | 313 ms | 9.75 ms | **101.86 ms / hit 0.09**（几乎全程回退） |
| `(1, 2, 4, 8, 16, 32)` | 5.17 GB | 445 ms | 9.92 ms | 10.14 ms / hit 1.00 |

**结论**：桶数从 3 档到 6 档的**显存代价可忽略（+0.02GB）**、捕获耗时 +132ms；
但**桶档不足会让超桶批全部回退**，代价是 10× 的 TPOT 劣化。
即：16GB 上瓶颈不在桶数，宁可多开桶也别让批溢出（与 roadmap §1「桶数要克制」的取舍方向一致，
但本次数据显示 6 档的显存边际成本远低于预期）。

### 4. 混合负载命中/回退与 padding 浪费（`p7_bench.json::hit_rate_mixed`）

- 负载：2×2048 长 prompt（分 chunk）+ 8×128 短 prompt，budget=2048
- 结果：**replays 33 / fallback 0（hit=1.00）**，`bucket_hist={1:2, 16:31}`，`padded_seqs=188`
- 解读：10 条并发 → 桶 16 → 每步浪费 6 行 padding（37.5%）。因 P7 只捕获 decode，
  prefill chunk 不进图（因此不产生回退），命中率仍 100%。
- **可优化项**：桶档在 8→16 之间过粗（10 条并发就多 37.5% 行）。若要压低 padding，
  可在 `1/2/4/8/16/32` 之外补 `12`（vLLM 也是按 `max_num_seqs` 反推 capture sizes 的）。
  但注意 padding 行的真实代价只是 lm_head 白算 + 拷贝，TPOT 影响在本次测量中未显著体现
  （bs=16 与 bs=32 的 TPOT 差 0.4ms），故列为**记录项**而非必修。

## 踩坑记录（bench 可信度相关，务必保留）

1. **`_profile_num_blocks` 按"当时剩余显存"反推** → 不同配置拿到不同池容量；小池触发抢占 → TPOT 被重算污染
   （曾出现 eager 138ms @ bs=2 的假数据）。**P7 bench 全部固定 `num_blocks=4096`。**
2. **反复创建 runner 会叠加显存**：每次 `NanoRunner` 重新加载权重（3.1GB）+ 新建 KV 池。
   **P7 bench 改为每种模式只建一个 runner 跨 batch 复用。**
3. **`del obj` 写在辅助函数里只删局部名**：调用方作用域仍持有 runner → 图池与权重叠加到 10–15GB，
   在 16GB 卡上触发 WSL 换页，出现 80ms+ 的假慢步。**必须调用点显式 `del` 再 `free_cuda()`。**
4. **闭包引用环**：bench 里 patch `engine._execute` 会形成 `engine → wrapped → bound method → engine`
   的环；已加 `restore()`（仍在 drop 前，双保险）。
5. **图输入布局**：必须是 `b = 桶、s = 1`（`input_ids.unsqueeze(1)`），写成 `b=1、s=桶` 会让
   attention 把整批当成「单请求多 token」而报 shape 错（`test_p7_correctness.py` 首轮即抓到）。
6. **微基准不要用「单轮 min」当口径**：本机（WSL + 单卡）噪声下单轮 min 会被偶发低值拉偏。
   实测 full-bucket 组 legacy 的 min 比其中位数低 17%，用 min-vs-min 会得出「改后更慢 0.94×」
   的**错误结论**；改 9 轮中位数后为 1.19×。故 `p7_fill_bench.py` 同时报告 median 与 min 两个口径。
7. **跨 run 的端到端数字不可直接归因**：同一份 profiler 脚本两次运行，**未被改动**的 eager 路径
   TPOT 也漂了 21%（45.28 → 35.59 ms）。判断「小改动有没有用」必须用同进程 A/B 对照，跨 run 只能看趋势。
8. **测图池显存必须在 `torch.no_grad()` 下**：grad 开启时 `logits` 的 `grad_fn` 链会吊住整条前向的
   中间激活 → 池无法回收。实测六桶捕获 `allocated` Δ **527MB（grad 开）vs 35MB（no_grad）**，差 15×。
   直接用 `graph_runner.capture()` 的 bench/诊断脚本必须自带 `no_grad`；引擎路径靠
   `EngineCore._decode_logits` 的 `@torch.no_grad()`（**该装饰器是承重设计，不只是加速**）。
9. **跨配置比显存时必须固定 grad 状态**：踩坑 8 的假象曾让「3 档 vs 6 档」测出 +0.36GB（真值 +13MB）。
   显存类对照（桶档/池共享）一律显式 `no_grad`，并在结论里写明口径。

## 补记 · 静态 buffer 填充改为单次 H2D（2026-10-03）

### 动机

§2 的 profiler 显示图化后 **CPU 侧总 API 时间 8.68ms ≈ TPOT 的 79%**，其中 memcpy 占 7.2ms。
而原 `fill()` 每一路都是「`torch.tensor(..., device=dev)` 建临时 GPU 张量 → 再 `copy_`」，
即 **alloc + H2D + D2D 两次传输**；缺失的 padding 行还要 6 次设备侧 `fill_` kernel。这些都是纯开销。

### 改法（`nano_vllm/cudagraph/buffers.py::fill`）

| 改造前 | 改造后 |
| --- | --- |
| 每路 `torch.tensor(list, device=dev)` + `copy_` → 2 次传输 + 1 次分配 | 整桶内容先在 host 侧构造完整，`self.input_ids.copy_(torch.tensor(toks))` → **1 次 H2D 直达** |
| padding 行用设备侧 `fill_`（6 次 kernel/step） | padding 值在 host 侧随整桶一起构造，**0 次 kernel** |
| `block_table[:n].zero_()` + `[:n, :max_len].copy_` | `[:, :max_len].copy_`（整桶含 padding 行）；尾部列在 `max_len < max_blocks` 时统一 `zero_()` |
| 半批时 buffer 处于「前 n 行新 + 后几行需另填」的两段状态 | 每类数据**一次写入整桶**，无中间态 |

语义不变：校验仍全部前置（raise 时 buffer 一个字未改），块表尾部仍清零，padding 行仍只指向 scratch 块。

### 数据（`bench/p7_fill_bench.py` → `bench/results/p7_fill_bench.json`）

同进程 A/B 交替、9 轮、取中位数（min 口径一并落盘，两者方向一致）：

| 用例 | legacy (µs/fill) | 单次 H2D (µs/fill) | 加速 |
| --- | --- | --- | --- |
| bucket=8, n=8（满桶，无 padding） | 265.1 | 222.4 | **1.19×** |
| bucket=8, n=5（半桶，含 padding） | 365.5 | 227.6 | **1.61×** |
| bucket=32, n=17 | 389.6 | 270.9 | **1.44×** |

- `buffers_identical=true`：两种实现写出的 5 个 buffer **逐元素一致**（脚本内置断言）。
- **收益归因**：加速主要来自「不再发 6 次设备侧 `fill_` kernel」——所以**有 padding 行时收益最大
  （1.44–1.61×）**，满桶时最小（1.19×）。去掉的 D2D/分配在满桶时仅约 20µs，落在噪声边缘。

### 诚实边界（为什么不一并给出端到端数字）

同参数重跑 profiler（`p7_profiler_single_h2d.json`）确实显示 memcpy 7162 → 6753 µs/step、
TPOT 10.96 → 8.04 ms；**但同一次运行里未被改动的 eager 路径也漂了 21%（45.28 → 35.59 ms）**，
说明该机器跨 run 漂移与本次效应同量级，**端到端差值不能归因于本次改动**。可信口径是同进程 A/B 的
`fill()` 微基准：每 decode step 一次 fill，省 43–162 µs ≈ TPOT(8–11ms) 的 **0.5–2%**。
（这两条已作为踩坑记录 6/7 保留。）

### 顺带发现（仅记录，未修）

`replay_static_eager`（归因实验路径）里 `_forward` 会**正常执行** `PagedKVCache.write()` →
`_written_tokens += bucket`，随后又 `note_written(n)` → 该路径的写入计数**双计**且含 padding 行。
仅影响 `waste_rate` 诊断指标的绝对值，不影响生产路径（图回放路径的 `note_written(n)` 准确）。
若日后要用 `waste_rate` 做跨路径对照，需先修此处。

### 剩余优化（归 P8/P9）

1. **pin memory + `non_blocking=True`**：目前 H2D 源是 pageable 内存，`copy_` 实为同步；
   换成持久 pinned staging buffer 才能真异步、与计算重叠。
2. **4 路合并为一次打包拷贝**：`[4, bucket]` 一次 H2D（甚至 5 路含块表头部）。
3. **块表按行差异更新**：只写变化的列，避免整表重写。
4. 大头仍在**采样 D2H**（argmax → host token id），属 P8/P9 的采样批量化课题。

## 补记 · 图池语义、显存口径与 vLLM 对照（2026-10-03）

> 背景：P7 完工后对「图池到底装什么、省多少、与官方实现差在哪」做了一轮复核。
> 期间**出过一次错误测量并据此"修正"了本文档**，教训一并记录。
> 证据：`bench/vllm_cudagraph_probe.py` → `bench/results/vllm_cudagraph_probe_{eager,graph}.json`。

### 1. 承重条件：测量图池必须在 `torch.no_grad()` 下

`EngineCore._decode_logits` 带 `@torch.no_grad()`（`nano_vllm/engine/core.py:198`）。这不只是加速
——**它直接决定图池大小**：

| 捕获时 grad 状态 | 六桶 capture `allocated` Δ |
| --- | --- |
| grad 开启（错误口径） | **527.17 MB** |
| `torch.no_grad()`（引擎真实路径） | **35.01 MB** |

**差 15×**。原因：grad 开启时 `logits` 的 `grad_fn` 链把所有中间激活吊住 → 捕获结束时它们仍被引用
→ 池无法回收 → 池要按「整条前向的全部激活」扩张。

正确口径下的逐桶增量（`no_grad`、共享池、升序）：

| bucket | 1 | 2 | 4 | 8 | 16 | 32 | 合计 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Δallocated (MB) | 16.55 | 0.60 | 1.19 | 2.38 | 4.76 | 9.53 | **35.01** |

除首桶 16.55MB（池初始化基线）外，增量精确等于 **0.30MB × bucket**，而 `logits` 每行正是
`151936 × 2B = 0.29MB`。即：**池里真正累积的只有「被保留的输出」，瞬态激活在捕获结束后回到池、
被后续捕获复用。**

### 2. 桶档显存：维持 §3 的 +0.02GB（撤回一次错误修正）

| 桶档 | 实测 current = peak allocated |
| --- | --- |
| `(1, 4, 16)` | 5.020 GB |
| `(1, 2, 4, 8, 16, 32)` | 5.033 GB |
| 差值 | **+13 MB** |

与 §3 的「+0.02GB，代价可忽略」一致，**原文正确**。（绝对值与 §3 的 5.15/5.17 差约 0.13GB，
因测量时刻不同——§3 在整轮 bench 后取 peak，本次在捕获后立即取；本轮要核对的是**差值**。）
复核中曾用带 grad 的口径测出 5.19 / 5.55 GB（差 0.36GB）并据此提出「应改为 +0.36GB」——
那是第 1 条假象造成的，**已撤回**。

### 3. 共享图池的显存收益：**待复核**（原注释「省显存」缺乏支持）

| 模式 | 六桶 `allocated` Δ | 池数 |
| --- | --- | --- |
| 共享同一池 | 26.89 MB | 1 |
| 每图独立池（`pool=None`） | 17.36 MB | 6 |

实测共享**反而略高 9.5MB**，与 `decode_graph.py:142` 注释里「省显存」的预期方向相反。量级很小
（20–35MB）且为单次实测，故列为**待复核**而非结论。共享池的其它价值（统一管理、顺序回放无别名）
不受影响。

### 4. 池的职责澄清：隔离，而非「固定地址」

- **地址固定**来自**保活**（持有引用）：输入 buffer、权重、KV cache 都是捕获前分配、我们持有引用 → 地址天然稳定
- **池的作用**是「**隔离**」：让那些**我们不打算保留**的瞬态张量也不会被通用分配器复用
  （回放时 kernel 用的是捕获时的绝对地址）
- 因此**输入 buffer 必然在池外**：`DecodeBuffers` 建在 `with torch.cuda.graph(...)` 之前
  （`decode_graph.py:129` vs `:143`），且捕获时要读它——「输入在池内」会形成循环依赖
  （要有池才能分配 → 要有分配才能捕获 → 要有捕获才有池）
- 实测佐证：把上一轮 `bufs` 提前回收，下一次 `capture_begin` 直接抛
  `RuntimeError: it->second->use_count > 0`（池内块不可提前释放）；输入 buffer 不在此列

### 5. 与 vLLM 0.29.0 官方实现的对照（同机实测）

环境：`~/venvs/vllm`（vLLM 0.29.0 / torch 2.13.0+cu132），`VLLM_USE_V2_MODEL_RUNNER=0`
（默认 V2 runner 需要 UVA，WSL 下不可用），Qwen2.5-1.5B，`max_model_len=1024`，`gpu_memory_utilization=0.45`。

| 指标 | vLLM 0.29.0 | nano P7 |
| --- | --- | --- |
| 捕获图数量 | **1574**（PIECEWISE 51 尺寸 + FULL 35 尺寸） | 6 |
| 图池数量 | **2**（`(0,2)` 60 次 / `(0,1)` 1514 次） | 1 |
| 图池显存 | **0.42 GiB**（官方自报；估算 0.49GiB，偏差 17.4%） | ~17–35 MB |
| 捕获耗时 | 4 s | 445 ms |
| 跨图复用瞬态激活 | ✅（`alloc_before` 从第 104 次起恒定 6217MB，ΣΔalloc 4.3GB 并未真的占用） | ✅（同构，见第 1 条） |
| 累积的只有输出 | 各图段输出 + `hidden_states` | 各桶 `logits` |
| 图池记账 | ✅ `actual vs estimated` 自报 | ❌ 仅事后实测 |

**不能直接比「每图显存」**：vLLM 是把 torch.compile 切出的约 30 个**图段**逐个捕获（每段只覆盖
少量算子），nano 一张图是整个 28 层前向。1574 : 6 来自**图粒度差异**，不是效率差异。

**复用行为的结论**：两者**本质一致**——捕获期间的瞬态激活在捕获结束后回到池并被后续捕获复用，
池里真正累积的只有被保留的输出。此前「vLLM 复用 / nano 不复用」的印象源于第 1 条的测量假象。

**两点结构差异**（记录即可，属裁剪）：
vLLM 也是**两个池**而非单一全局池（PIECEWISE / FULL 各一）；且其捕获顺序是**降序**（大图先，
代码注释为复用内存池），nano 为升序——实测两种顺序对 nano 的总量无影响。

## 补记 · P1 logits 移出图 + P2 共享输入缓冲（2026-10-03）

> 两项都是**向 vLLM 官方实现对齐**的改造，来源见本文件「补记 · 图池语义…」第 5 节。
> 证据：`bench/results/p7_p1p2_pool.json`、`bench/results/p7_profiler_p1p2.json`。
> 全量测试 **130 passed**；`test_p7_correctness.py` 10 项（含边界 batch）绿。

### P1 · lm_head 移出图（图输出 hidden_states，logits 图外算）

**vLLM 依据**：`sample_hidden_states = hidden_states[logits_indices]` →
`logits = self.model.compute_logits(sample_hidden_states)`
（`gpu_model_runner.py:4509-4510`，`logits_indices = query_start_loc[1:] - 1` 于 `:2253`）。

| 项 | 改造前 | 改造后 |
| --- | --- | --- |
| 图输出 | `logits [bucket, 151936]` bf16 | **`hidden [bucket, 1536]`** bf16 |
| bucket=32 图输出 | 9.27 MB | **0.094 MB**（**99× 小**） |
| 六桶输出合计 | 18.5 MB | **0.19 MB**（**97× 小**） |
| padding 行白算 lm_head | 有（10 并发→桶 16 时 37.5% 行） | **消失**（只算 `[:n]`） |

**关键论证（为什么不只是"更小"）**：**图内躲不掉 padding 行的白算**——静态形状决定行数，
即便传 `last_idx` 也必须是固定索引，而 padding 行就落在 `[0, bucket)` 里。所以"移出图"
是**唯一解法**，不是优化选项。

**实现**：`qwen2.py` 新增 `skip_lm_head=True` 分支（图内直接返回 hidden）+
`compute_logits(hidden_states)`（图外投影）；`decode_graph.py::_forward` 返回
`hidden[:, 0]`；`core.py::_decode_logits` 在图外调 `compute_logits`。
nano 的 decode 批每行恰 1 token，故 vLLM 的 `hidden_states[logits_indices]` 在本实现里
**退化为 `hidden[:n]`（无 gather）**。

### P2 · 输入缓冲：一套按最大桶分配 + `[:bucket]` 前缀视图共享

**vLLM 依据**：persistent buffers 按 `max_num_tokens` 分配一次，
每步只写 `[:num_tokens_padded]` 切片（`gpu_model_runner.py:812-825`）。

| 项 | 改造前 | 改造后 |
| --- | --- | --- |
| 输入缓冲套数 | 6（每桶一套） | **1** |
| `block_table` 总量 | 516 KB（6 桶求和） | 263 KB |
| 六桶 capture `allocated` Δ | 35.01 MB | **16.43 MB**（**2.13× ↓**） |
| 桶档 6 档相对 3 档 | +13 MB | **+1 MB** |

**安全性论证**：捕获/回放传的都是 `buf[:bucket]` **前缀视图**——`data_ptr()` 与整条 buffer
相同、stride 相同，而 kernel 只碰 `[0, bucket)` 行，所以桶 b 的图永远读不到桶 b' 的行；
回放又是顺序的（一个 step 一张图）。实测 `graph_pool_probe.py` 已确认：
**6 个桶的 `input_ids` 指针完全一致**、6 个 `hidden` 输出地址**互不相同**、
桶 32 回放后桶 1 的输出未被改写（无别名）。

**关于 `is_padding` 掩码：故意不做。** vLLM 里它只服务 **MoE 专家路由**跳过 padding token
（`VLLM_MOE_SKIP_PADDING`，消费者全是 deepseek/kimi 系 MoE 模型，见
`deepseek_v4/nvidia/fi_moe.py:60-67`），dense 模型没有消费者——加了是死代码。
nano 的 padding 隔离由 scratch 块完成。

### 实测对比（同一会话三次 profiler，batch=8）

| 指标 | 基线 | 单次 H2D 后 | **P1+P2 后** | eager 漂移参照 |
| --- | --- | --- | --- | --- |
| TPOT（图） | 7.89 ms | 8.04 ms | **7.89 ms** | 37.79 → 35.59 → 39.94 ms |
| 捕获耗时 | 484 ms | 473 ms | **435 ms** | — |
| memcpy/step | 6456 µs | 6753 µs | **6584 µs** | — |
| kernel launch/step | 76.0 µs | 55.8 µs | **38.2 µs** | — |

**读法**：图路径各项持平或略好（launch -32%），而**未被改动的 eager 路径在同会话内漂了
+12%** —— 结论只能取"**无劣化、方向符合预期**"，不能声称 TPOT 变快。
（`capture_ms` 另注：`p7_profiler.py` 的捕获发生在 prefill 之后，此时 Triton kernel
已编译，故 435ms；若在**全新进程直接 `capture()`**，warmup 要现场编译，实测 909–1298 ms。
两者不可比。）

### 顺带修正：4 个 pool probe 脚本补上 `no_grad`

`graph_pool_{mem2,order,probe,weakref}.py` 原本未开 `no_grad`（违反踩坑 8）。
补 `torch.set_grad_enabled(False)` 后，`graph_pool_probe.py` 报的图池占用
**612 MiB → 124 MiB（4.9×）**，再次印证该约束。这 4 个脚本同时已适配 P1/P2 的新 API
（单一 `gr.buffers`、`gr.outputs[bucket]`、`_forward(bucket)`）。
